# Autenticação, Perfis e Colaboração

Autenticação via **Spring Authorization Server embutido no próprio backend** (`AuthorizationServerConfig`) — OAuth2 Authorization Code + PKCE, tokens RSA assinados, validados por JWKS (`/oauth2/jwks`). As *claims* do access token continuam nomeadas como o Keycloak nomeia as suas (`sub`, `preferred_username`, `realm_access.roles`) de propósito, para que uma futura migração para o Keycloak real troque só `issuer-uri`/registro do client, sem tocar `DocumentoAcessoService`/`@PreAuthorize` nem o restante da lógica de autorização.

## Login e sessão

- **Login por CPF + senha**, com um fluxo OAuth2 Authorization Code + PKCE (não um POST JSON direto): a SPA (`fab-legis-frontend`, client **público**, sem secret) navega de verdade para `/oauth2/authorize`; se não autenticado, o Authorization Server redireciona para a própria `LoginPage.vue`, que renderiza o formulário e o submete via **POST HTML tradicional** (não `fetch`) para `/login` no backend — só assim o cookie de sessão do Spring Security e a cadeia de redirects de volta para `/oauth2/authorize` funcionam. Autenticado, o backend emite um `code` e redireciona para `/callback` (`OAuthCallbackPage.vue`), que troca o `code` por um **access token** via `POST /oauth2/token` (PKCE `code_verifier`, gerado e guardado em `sessionStorage` só durante o handshake).
- **`/oauth2/**`, `/login` (POST) e `/logout` são proxiados pelo próprio dev server do Vite** (`server.proxy` em `frontend/vite.config.js`) para o backend — do ponto de vista do navegador, toda essa troca acontece na MESMA origem do frontend (`127.0.0.1:5173`), nunca como uma chamada cross-origin para `127.0.0.1:8081`. Isso é essencial, não só uma otimização: o cookie de sessão do Spring Security é `SameSite=Lax` (padrão), e uma navegação de topo POST cross-origin só carrega esse cookie numa janela curta logo após ele ser criado (mitigação "Lax+POST" do Chrome) — suficiente para testes automatizados rápidos, mas não para uma pessoa digitando CPF/senha em ritmo normal. Sem o proxy, o login "funcionava" (POST 200/302) mas autenticava numa sessão nova sem a `/oauth2/authorize` pendente salva, caindo de volta no login sem erro nenhum. Em produção (Nginx, `frontend-prod`) esse mesmo perfil — tornar tudo mesma-origem — é do reverse proxy do próprio Nginx, não do Vite.
  - **Acesse sempre via `http://127.0.0.1:5173`, nunca `http://localhost:5173`** — são origens diferentes para o navegador (cookie de sessão e `sessionStorage` não atravessam), e o `redirect_uri` do client OAuth2 está registrado só para `127.0.0.1` (por segurança: `redirect_uri` exige correspondência exata, registrar os dois abriria uma brecha). Acessar via `localhost` quebra o fluxo já no primeiro `/oauth2/authorize`.
- **Access token JWT de vida curta** (30 min). **Não há refresh token**: o Spring Authorization Server nunca emite refresh token para um client público (`ClientAuthenticationMethod.NONE`) — decisão de segurança do próprio framework, não uma escolha deste projeto (um refresh token é um credential de longa duração; dar um a um client que não consegue se reautenticar depois reintroduziria o risco que o PKCE existe para evitar).
- `stores/auth.js` faz uma **renovação silenciosa** (`refresh()`) via iframe oculto reautorizando `/oauth2/authorize` com o cookie de sessão ainda válido. Graças ao proxy acima, essa reautorização também acontece em mesma-origem (o `src` do iframe é `/oauth2/authorize`, relativo à própria página) — o cookie `SameSite=Lax` é enviado normalmente (a restrição de `SameSite` só se aplica a requisições cross-*site*, e esta não é uma) e o iframe recebe o `code` direto, sem passar pelo login. Quando a renovação silenciosa falha mesmo assim (sessão do backend expirada de verdade), `client.js` desloga e manda para o login de novo — comportamento seguro, só menos conveniente que uma renovação transparente.
- Logout (`AppTopBar.vue` → `auth.logout()`) é uma **navegação de página inteira** (`window.location.href = .../logout`, proxiado) — a navegação de topo é a forma mais simples e robusta de garantir que o cookie de sessão (`SameSite=Lax`) seja enviado e a sessão certa seja encerrada; um `fetch()` cross-origin não o levaria. `logoutSuccessUrl` já aponta de volta para `/login`.
  Antes de navegar, o logout **limpa tudo o que a sessão deixou no navegador** (`limparCachesDaSessao`): o token do `localStorage`, o estado de todas as stores do Pinia (`$reset` em cada uma — documentos, painel, busca, editor, autenticação) e o cache de URLs assinadas do MinIO. A página inteira é recarregada em seguida, o que já descartaria a memória, mas a limpeza explícita não depende disso (vale também no logout forçado por token expirado) e uma store nova entra nela sozinha.
- **Formulário de login e gerenciador de senhas:** o CPF (`autocomplete="username"`) e a senha (`name="password"`, `autocomplete="current-password"`) são campos visíveis do próprio formulário, para o navegador oferecer salvar e preencher as credenciais; só o CPF sem máscara viaja num campo oculto (`username`).

!!! note "Detecção de expiração é reativa, por design"
    A validade do token só é verificada no momento em que uma chamada real à API acontece através do `client.js` — ou quando a conexão SSE de notificações (`AppTopBar.vue`) recebe um erro de autenticação do servidor. Não há timer proativo de logout — se o usuário ficar numa página já carregada sem disparar nenhuma requisição e sem receber nenhum erro do SSE, a sessão pode *parecer* válida até a próxima interação real. Essa é uma decisão deliberada, não um bug.
    
    O `EventSource` de notificações leva o token na própria URL (não há header em SSE); quando ele expira, o servidor rejeita a conexão e o navegador **não** tenta de novo sozinho (`readyState` vai direto para `CLOSED` — só reconecta automaticamente em queda de rede, não em erro de autenticação). `AppTopBar.vue` detecta esse `CLOSED` e reage: tenta uma renovação silenciosa (`auth.refresh()`) e, se conseguir, reconecta o SSE com o token novo; se não conseguir, desloga.

## CPF oculto na tela

O CPF é **dado pessoal**: em toda tela onde ele fica visível para um usuário — menu do usuário (o próprio CPF), lista de Manter Usuários e formulário de edição, coautores e seletores de pessoa (revisor/publicador), Auditoria — aparece **ocultado como no Portal da Transparência**, só com os 3 primeiros e os 2 últimos dígitos: `111.***.***-35` (`ocultarCpf` em `frontend/src/utils/cpf.js`; um valor malformado nunca é devolvido, sai totalmente oculto). Os campos em que a própria pessoa **digita** um CPF — login e cadastro de um novo usuário — continuam mostrando o que ela digita, e o CPF de um usuário existente não é editável. Isto é só exibição: a API ainda devolve o CPF completo onde a tela precisa dele para identificar a pessoa (ex.: compartilhar um documento envia o CPF do coautor escolhido).

## Perfis e posse de documento

Nenhum poder sobre o ciclo de vida de um documento é implícito — todos os perfis são concedidos explicitamente na tela **Manter Usuários** (restrita a administradores), em `PapelEnum`. Uma pessoa sem perfil nenhum só visualiza o acervo. Cada perfil tem **código** (o que vai para o banco e para o token) e **nome por extenso** (o que as telas mostram), guardados no enum e na tabela `t_papel` (migração `V21`, conferidos por `PapelEnumIntegracaoTest`); o **escopo** (geral ou da OM) está no próprio código:

| Código | Nome por extenso | O que faz |
|---|---|---|
| `ELB` | **Elaborador** | Cria documentos e edita (inclusive os **anexos**, que seguem a mesma regra de edição) / exclui (em Rascunho/Minuta) os que autorou ou dos quais é coautor; move o documento entre as etapas de elaboração e o **envia para aprovação**. Todo usuário tem este perfil |
| `APR_OM` | **Aprovador da OM** | Age nos documentos da **própria OM** que aguardam aprovação (`EM_REVISAO`/`ANALISE_REVOGACAO`) — qualquer aprovador da OM, ninguém é escolhido: aprova (o documento segue para a fila de publicação do CENDOC) ou devolve. Também pode, livremente, reabrir para alteração qualquer documento publicado da própria OM (`SEM_ETAPA → EM_ALTERACAO`) e cancelar uma alteração em curso sem alterações pendentes (`EM_ALTERACAO → SEM_ETAPA`) |
| `PUB_BCA` | **Publicador do BCA** | Exclusivo do **CENDOC** (a publicação no BCA é dele). Age em qualquer documento que aguarda publicação (`EM_PUBLICACAO`/`EM_REVOGACAO`), de qualquer OM — qualquer publicador, ninguém é escolhido: publica (podendo devolver) ou revoga (com portaria/BCA e parte preliminar; uma revogação aprovada não é devolvida) |
| `AUD_OM` | **Auditor da OM** | Consulta a trilha de auditoria (tela **Auditoria**) **da própria OM** |
| `AUD_GER` | **Auditor Geral** | Consulta a trilha de auditoria **de todas as OMs**; exclusivo do CENDOC |
| `ADM_OM` | **Administrador da OM** | Gerencia os **usuários da própria OM** (ver [Escopo de acesso](#escopo-de-acesso-geral-e-local)); puramente administrativo: não edita, aprova nem publica documento nenhum |
| `ADM_GER` | **Administrador Geral** | Gerencia os usuários de **todas** as OMs e os administradores das OMs; cadastra habilitação de espécies e DOM; exclusivo do CENDOC. Também puramente administrativo |
| `GES_OM` | **Gestor da OM** | Consulta os indicadores do [Painel Gerencial](funcionalidades.md#painel-gerencial) **da própria OM** (filtrados automaticamente); não altera nada |
| `GES_GER` | **Gestor Geral** | Consulta os indicadores do Painel Gerencial **de todas as OMs**, com filtro por OM; exclusivo do CENDOC. O usuário padrão do sistema nasce com este perfil |

O Auditor (da OM ou Geral) é independente do Administrador: quem administra **não** enxerga a auditoria automaticamente, precisa ter o perfil de auditor. Cada perfil só combina com a lotação certa: `ADM_GER`, `AUD_GER`, `GES_GER` e `PUB_BCA` só existem lotados no CENDOC; `ADM_OM`, `AUD_OM` e `GES_OM`, nas demais OMs (o sistema recusa o resto, com a regra na mensagem).

**Quem pode editar um documento, e quando** (`DocumentoAcessoService.podeEditar`, a checagem de todo endpoint que altera o documento e a que o servidor de colaboração consulta em `GET /documentos/{id}/pode-editar`): em `RASCUNHO`, `MINUTA` e `EM_ALTERACAO`, o autor e os coautores com perfil Editor; em `EM_REVISAO`, **só** os aprovadores da OM do documento (e só se o documento ainda não foi publicado — nem o autor edita durante a revisão); em qualquer outra etapa (`EM_PUBLICACAO` em diante, todo o fluxo de revogação, `CANCELADO`, `SEM_ETAPA`) ninguém, nem o autor. **Mudar de etapa e excluir** dependem da *posse* do documento (autor/coautor com perfil Editor), não de poder editar o conteúdo naquela etapa — por isso o autor ainda pede a revogação de um ato publicado, mesmo com o conteúdo congelado. **Enviar o PDF da portaria** (`POST /documentos/{id}/portaria-pdf`) é de um publicador (CENDOC), com o documento em `EM_PUBLICACAO` ou `EM_REVOGACAO` (`podeEnviarPortaria`) — a mesma pessoa que registra a publicação.

**Sem atribuição pessoal — "Enviar para aprovação":** ao enviar um documento para aprovação (ou pedir a análise de revogação) o Editor **não escolhe ninguém**: o documento fica disponível para **qualquer aprovador da OM do documento** (`DocumentoAcessoService.ehAprovadorDaOm`), que também são avisados por notificação; ao aprovar, ele vai para a fila de publicação do CENDOC, onde **qualquer publicador** age (o perfil `PUBLIC` só existe no CENDOC — ver [Escopo de acesso](#escopo-de-acesso-geral-e-local)). O que fica registrado é *quem aprovou* (`Documento.aprovador`, o "Aprovado por" da NPA) e *quem publicou* (`Documento.publicador`), por quem de fato agiu. Ninguém precisa estar disponível: férias ou troca de comando não travam um documento. Ver [Ciclo de Vida do Documento](ciclo-de-vida.md) para o fluxo completo.

**Coautoria:** o autor de um documento pode adicionar outros usuários como coautores (`DocumentoCompartilhamentoService`) — um coautor ganha os mesmos direitos de edição/exclusão do autor sobre aquele documento específico, mas só o autor pode gerenciar a lista de coautores. A busca no `CompartilharDialog.vue` é por **nome de guerra ou nome completo** (`GET /usuarios/buscar?q=`), nunca por CPF digitado — CPF é dado pessoal que o autor raramente sabe de cor; o CPF do usuário escolhido é resolvido internamente a partir do resultado da busca e só então enviado ao backend (`compartilhar`, que continua identificando o coautor por CPF). Diferente do seletor de revisor/publicador (escopado à OM de quem escolhe), essa busca é **sem filtro de OM**, coerente com a coautoria em si não ser restrita a isso (ver abaixo). A OM nunca é barreira pra coautoria: o documento aparece em "Meus Documentos" pro autor e pra todo coautor, **qualquer que seja a OM de cada um** (`DocumentoSpecifications.aba`), refletido ali em tempo real assim que o compartilhamento acontece, via a mesma notificação SSE `DOCUMENTO_COMPARTILHADO` do sino de notificações. Já "Documentos da Minha OM"/"Documentos de Outras OMs" continuam decididos só pela OM do documento em si (a OM do autor no momento da criação), sem olhar autoria/coautoria — por isso essas abas propositalmente **se sobrepõem** a "Meus Documentos" em vez de excluí-la: um documento da OM A com um coautor da OM B aparece em "Meus Documentos" **e** "Documentos da Minha OM" pra quem é da OM A, mas em "Meus Documentos" **e** "Documentos de Outras OMs" pro coautor da OM B.

## Escopo de acesso (geral e local)

O acesso tem **escopo**: só o **CENDOC** tem o escopo **geral**; toda outra OM tem escopo **local** (`EscopoDeAcesso`). O escopo está no próprio perfil (`ADM_GER`/`AUD_GER` são do CENDOC; `ADM_OM`/`AUD_OM`, das demais OMs) e o login ganha uma authority por perfil, pelo código (`ROLE_ADM_GER`, `ROLE_AUD_OM`…) para o `@PreAuthorize`.

| | **Geral** (CENDOC) | **Local** (outra OM) |
|---|---|---|
| **Administrador** (`ADM_GER` / `ADM_OM`) | Vê e gerencia os usuários de **todas** as OMs; mantém os **administradores das OMs** (só ele concede `ADM_OM`); cadastra **habilitação de espécies** e **DOM** (`Manter Habilitação…`, `Manter DOM de OM`) | Vê e gerencia **só os usuários da própria OM**; concede **Elaborador, Aprovador da OM e Auditor da OM**; **nunca** concede `ADM_OM` nem `PUB_BCA`; não altera outro administrador; não muda um usuário de OM |
| **Auditor** (`AUD_GER` / `AUD_OM`) | Trilha de auditoria **completa** (documentos e acessos) | Só o que é da **própria OM**: ações dos usuários dela e acessos a eles |

- **O admin local nunca extrapola o escopo.** Um usuário de outra OM nem aparece para ele (404, como se não existisse), e qualquer tentativa de criar ou mudar fora da própria OM, conceder `ADM_OM` ou mexer em outro administrador responde **403** com a regra violada. A tela de usuários já mostra só o que vale (OM fixa, perfis desabilitados com explicação); o servidor é quem garante.
- **Publicador só no CENDOC:** a publicação no BCA é do CENDOC, então o perfil `PUB_BCA` só existe para quem é da OM CENDOC — recusado para qualquer outra OM, inclusive pelo admin geral.
- **Administrador Geral só no CENDOC:** `ADM_GER` (e `AUD_GER`, `PUB_BCA`) só existem para quem é **lotado no CENDOC** — o sistema recusa concedê-los a quem é de outra OM, e recusa `ADM_OM`/`AUD_OM` a quem é do CENDOC (lá, use o geral). E o CENDOC **nunca fica sem Administrador Geral**: o último `ADM_GER` ativo não pode perder o perfil, ser desativado nem mudar de OM (`EscopoDeAcesso.exigirAoMenosUmAdminGeral`) — conceda o perfil a outra pessoa do CENDOC antes.
- Quem cria os usuários hoje é o admin: o geral cria o primeiro admin de cada OM e o admin local cria os demais da sua OM (não há como saber a lotação do militar enquanto o login é local; com o SSO da FAB cada pessoa se autocadastra, sempre com escopo local — ver o [roadmap](roadmap.md)).
- Todos continuam **vendo todos os documentos de todas as OMs** e alterando só segundo as regras de posse (autor/coautor), como antes.

## Habilitação de documentos

**Nem toda OM pode criar documentos de espécies normativas convencionais.** Só criam (MCA, NSCA, ICA, ROCA, DCA, FCA, OCA, PCA, RCA, RICA, TCA…) as organizações militares que o administrador do sistema (o **CENDOC**, perfil `ADMIN`) **habilitou** para a espécie. A **NPA** (Comunicações Oficiais Padronizadas) é criada por **qualquer** OM.

**O que a habilitação controla — só a criação.**

| Quem | Consulta (hub e módulo) | Cria | Clona | Coautor (edita o que lhe foi compartilhado) |
|---|---|---|---|---|
| Pessoa de **OM habilitada** na espécie | sim | sim | sim | sim |
| Pessoa de **OM sem habilitação** | **sim, normalmente** | não — o botão **não aparece** | não — o botão não aparece | **sim**: pode ser coautora de documento de OM habilitada |
| NPA, qualquer OM | sim | sim | sim | sim |

Ou seja, as espécies convencionais continuam aparecendo no hub e no módulo para todos; o que some, para quem não é de OM habilitada, é o botão de **criar** (o **Criar** do hub só lista os módulos em que a OM cria, e o botão **Novo Documento** do módulo) e o de **clonar**, que também cria um documento. O perfil `EDIT` continua necessário para criar; a habilitação é uma segunda condição.

**Padrão do primeiro boot:** apenas o **GABAER** e o **CENDOC** podem criar **todas** as espécies convencionais (`HabilitacaoPadraoRunner`, que só age enquanto não existe nenhuma habilitação gravada: depois disso a tabela é do administrador, e uma habilitação removida por ele não volta). O administrador padrão nasce na OM do CENDOC. Uma espécie convencional nova não é habilitada sozinha para ninguém: o administrador a habilita.

**Gestão — tela *Manter Habilitação de Espécies Normativas por OM*** (menu do usuário → *Manter Habilitação de Espécies Normativas por OM*, só `ADMIN`; `HabilitacaoDeDocumentosPage.vue`): **uma linha por espécie convencional** (cerca de uma dúzia), cada uma com as **OMs habilitadas a criá-la**, em chips que mostram só a **sigla**, e um seletor com busca (por sigla ou nome) para adicionar ou remover OMs. Foi escolhida a visão por espécie, e não uma linha por OM, porque quase nenhuma OM tem habilitação: a tela fica curta, sem linhas vazias, e responde direto "quem cria DCA?". A pergunta inversa ("o que a OM X cria?") é do filtro **Ver o que uma OM pode criar** no topo, que marca as espécies em que a OM aparece e conta quantas ela cria. Cada mudança é gravada na hora (e desfeita com aviso se o servidor recusar); *Remover todas as OMs* limpa uma espécie. A NPA não aparece, porque não depende de habilitação. Ficou como tela separada de *Manter Usuários*: não existe um cadastro de OMs ("Manter OMs") onde ela coubesse.

**Como é aplicada.**
- A espécie diz se exige habilitação: `RegraDeHabilitacaoDaOm.exigeHabilitacaoDaOm()`, uma das interfaces de regra por espécie (convencional: sim; NPA: não) — nunca um `if` na sigla.
- O backend barra: `DocumentoService.create` e `clone` chamam `HabilitacaoDeCriacaoService.exigirPodeCriar`, e uma OM sem habilitação recebe **403** com a mensagem "A sua organização militar não está habilitada a criar documentos da espécie X. Peça a habilitação ao administrador do sistema (CENDOC)." (`OperacaoNaoAutorizadaException`).
- O frontend esconde o botão: `GET /v1/habilitacao-de-documentos/minhas` devolve as espécies que a OM de quem pergunta cria, e a store de autenticação (`especiesCriaveis`) decide onde aparecem o **Criar** do hub, o **Novo Documento** do módulo e o **Clonar**, e quais espécies o seletor do diálogo de novo documento oferece. Enquanto a lista não carrega, nenhum botão de criar aparece.
- Os dados ficam em `t_om_especie_habilitada` (OM × espécie; migration `V14`).

## Edição concorrente

Em RASCUNHO/MINUTA, duas peças complementares — uma para o *conteúdo* de cada elemento, outra para a *estrutura* da árvore:

- **Colaboração ao vivo por elemento (CRDT/Yjs)** — o texto de cada artigo/parágrafo/inciso é editado através do serviço `collab` (Node.js + [Hocuspocus](https://tiptap.dev/docs/hocuspocus/introduction), ver [Arquitetura](arquitetura.md)): duas pessoas no mesmo elemento veem as letras uma da outra em tempo real, com *merge* automático, sem tela de conflito. A persistência no Postgres acontece em paralelo (debounced 2s, até 10s sob digitação contínua de qualquer um dos presentes), mas a visualização entre colaboradores não depende de salvar. Elementos ainda não persistidos (recém-criados, sem id do backend) usam um modo local simples até o primeiro salvamento.
    - O indicador "Salvando…"/"Salvo" do topo reflete o momento real da persistência no Postgres, não o ACK (quase instantâneo) do WebSocket — o `collab` avisa os navegadores conectados via mensagem *stateless* a cada alteração e a cada gravação concluída (ou falha).
    - A prévia do documento (painel PDF aproximado) também se atualiza em tempo real conforme qualquer pessoa digita no elemento aberto, sem esperar o debounce.
    - Uma falha ao persistir (ex.: token expirado em sessões de edição muito longas) é registrada e sinalizada ao navegador ("Não salvo"), mas nunca derruba o serviço `collab` inteiro — um erro de um elemento não pode tirar a colaboração de todos os outros documentos do ar.
- **Mudanças estruturais em tempo real** — criar, mover ou excluir um elemento (não é edição de texto, é mudança na árvore) é salvo por *diff* contra o que já está persistido (`PATCH /{id}/secoes`, nunca reescreve o `conteudo` de um elemento existente) e propagado aos demais navegadores conectados via o mesmo canal SSE de presença (`event: estrutura`) — a árvore de quem mais está editando se atualiza sozinha, por *patch* incremental (nunca um recarregamento completo, que interromperia quem estiver digitando ao vivo em outro elemento). Cada aba gera um id próprio (`clientId`) enviado junto com o salvamento e devolvido no evento, para que quem originou a mudança ignore o próprio eco. Se o elemento excluído era o que você tinha aberto, o editor fecha sozinho com um aviso.
- **Presença ao vivo** — enquanto o editor está aberto, a mesma conexão **SSE** (`GET /{id}/presenca/stream`) informa em tempo real quem mais está editando o mesmo documento (banner + toast, `event: presenca`); "quem está editando" é literalmente "quem tem essa conexão aberta agora" — sem heartbeat, sem polling, sem tabela própria no banco.
- **Bloqueio otimista por versão** — reservado a metadados do documento (título) e, na prática, raramente acionado hoje que conteúdo e estrutura têm seus próprios mecanismos de concorrência acima; cada documento carrega um número de versão (`nr_versao`), e o backend rejeita com `409` se a versão enviada não bater com a atual (`DocumentoConcorrenciaService`).

## Notificações e auditoria

- **Notificações em tempo real** (sino no topbar, via SSE) — gravadas na mesma transação da ação que as gera e entregues ao vivo a quem estiver conectado: documento compartilhado com você, ou documento aguardando a aprovação da sua OM (para os aprovadores da OM) ou aguardando publicação (para os publicadores do CENDOC) — ver perfis acima.
- **Trilha de auditoria** (`LogAuditoria`) — quem visualizou, criou, editou, excluiu, clonou, mudou situação ou (des)compartilhou cada documento, e quando; consultável e filtrável por quem tem o perfil Auditor na tela **Auditoria**. O registro sobrevive à exclusão do documento (guarda um retrato do código/descrição no momento da ação, não uma referência viva — pelo mesmo motivo, nunca uma FK para a linha do elemento em si, que pode ser excluída ou sobrescrita depois). Cobre também o salvamento granular da colaboração em tempo real (`PATCH .../elementos/{id}/conteudo`), registrado em cima do que já é persistido pelo Hocuspocus (que já debouncha essa chamada — 2 a 10s, nunca por *keystroke*), então não adiciona volume além do que a própria colaboração já gera. Uma falha ao gravar a auditoria em si nunca derruba a ação de negócio (fica só num log de erro) — a ação já foi commitada antes desse registro ser tentado.

### Auditoria de acessos

Além da trilha de documentos, toda mudança no **acesso de um usuário** deixa registro (`LogDeAcesso`, tabela `t_log_acesso`): **criação** do usuário, **concessão ou retirada de perfil**, **ativação/desativação**, **troca de OM** e **redefinição de senha**. Cada registro guarda quem fez (nulo = o próprio sistema, como no administrador padrão do primeiro boot), o usuário afetado (um *snapshot*: id, CPF, nome e a sigla da OM no momento, para a trilha sobreviver a mudanças posteriores do cadastro), a ação, o detalhe ("Concedido(s): APROV. Perfis agora: APROV, EDIT"; "BAGL → CENDOC") e a data.

- **Atomicidade:** o registro é gravado **na mesma transação** da mudança (`AuditoriaDeAcessoService`, ao contrário da auditoria de documentos, que engole a falha): conceder um perfil sem deixar rastro é pior do que não conceder. Editar um usuário sem mudar perfis, situação nem OM não gera registro (`DiferencaDeAcesso`: só o que de fato mudou, um evento por tipo de mudança).
- **Consulta:** `GET /v1/auditoria/acessos` (filtros: CPF do usuário afetado, ação, período), na aba **Acessos** da tela *Auditoria* — só o perfil `AUDITOR`, como a auditoria de documentos.

### Revisão periódica de acessos

Quem tem perfil **elevado** (qualquer um além do Editor: Aprovador, Publicador, Auditor, Administrador) precisa ter o acesso **reconfirmado** (`RevisaoDeAcesso`):

| Quando | Motivo na lista |
|---|---|
| 180 dias (6 meses) desde a última revisão | *Revisão vencida* |
| Ao **trocar de OM** (a revisão fica pendente de imediato) | *Trocou de OM* |
| Conta 180 dias sem entrar (`dt_ultimo_acesso`, gravada a cada login) | *Sem entrar há 6 meses* |

Conceder um perfil elevado novo (ou criar o usuário com ele) conta como revisão: o prazo corre dali (`dt_revisao_acesso`).

**Quem revisa quem:** o **admin geral** (CENDOC) confere **só os admins locais** e o pessoal do próprio CENDOC; cada **admin local** confere os **demais usuários da própria OM**. Ninguém revisa o próprio acesso, e quem não é admin não revisa ninguém.

**Como:** **automático** — o sistema calcula, para cada usuário, se o acesso precisa de revisão e mostra na tela **Manter Usuários** (coluna *Acesso*, faixa de aviso com o filtro "só os pendentes"). **Ninguém pede nada**: nem o usuário com perfil elevado, nem o admin; o admin só confere, nas linhas que lhe cabem, com **Manter acesso** (reconfirma os mesmos perfis) ou **Retirar perfis…** (desmarca o que a pessoa deixa de ter). A revisão **nunca concede** (conceder é editar o usuário), grava a data e registra `REVISOU_ACESSO` — mais o `ALTEROU_PAPEIS` do que foi retirado — na [auditoria de acessos](#auditoria-de-acessos), na mesma transação.

**Por ora só avisa:** as pendências aparecem na lista e na faixa de aviso da tela; **nada é suspenso nem desativado sozinho** (a suspensão dos perfis depois de uma carência e a notificação ao revisor ficam no [roadmap](roadmap.md)).
